# 软件开发自动化工作流：开源选型与落地路线

> 目标读者设定：主力工具 **Codex + GitHub Copilot + Claude Code**，先个人跑通，之后推广到团队。
> 数据抓取时间：2026-10-16。star 数来自 `ungh.cc` 代理 + `shields.io` 徽章交叉核对（本机直连 `api.github.com` 被限流），**star 仅作参考，不作为选型第一依据**。

## 0. 先说结论

### 三句话

1. **别一开始就装框架。** 先用 `AGENTS.md` + 少量 `skills` 把"你希望 agent 怎么干活"写下来，零锁定成本；框架的价值只是给这套东西加纪律。
2. **你选的三个工具的共同语言就是 `AGENTS.md`。** 一份根目录 `AGENTS.md` 三个工具通吃，只要再补两行胶水。
3. **每次只加一层，且新加的东西必须复用已写好的 `AGENTS.md`／`skills`**；否则你就是在制造第二个真相源，越迭代越乱。

### 推荐组合（个人起步 → 团队）

| 层 | 选谁 | 为什么 |
|---|---|---|
| ① 指令底座 | **手写 `AGENTS.md`**（+ `CLAUDE.md` 一行 `@AGENTS.md`） | 唯一跨 Codex/Copilot/Claude Code 的共识格式，零依赖 |
| ② 规格层 | **OpenSpec**（首选，轻）／ **spec-kit**（重但官方、生态最厚） | 让"要做什么"先落成文件，再让 agent 写代码 |
| ③ 规范注入 | **agent-os**（buildermethods） | 纯 markdown，把你的代码规范抽成 standards 按需注入 |
| ④ 素材库 | **obra/superpowers**（直接用）+ **wshobson/agents**（按 plugin 挑） | 一个改 agent 的工作方式，一个提供按需取用的 agent/skill |
| ⑤ 团队自动化 | **anthropics/claude-code-action** | 在你自己的 runner 上、由 PR/issue 事件触发的第一块团队底座 |

### 明确避开（本可以踩的坑）

| 项目 | 问题 |
|---|---|
| [gsd-build/get-shit-done](https://github.com/gsd-build/get-shit-done) | **已归档**（archived），却还挂着 ~64k star；续作是 [open-gsd/gsd-core](https://github.com/open-gsd/gsd-core)，但默认分支是 `next` |
| [catlog22/Claude-Code-Workflow](https://github.com/catlog22/Claude-Code-Workflow) | **已归档**（~4 个月无提交），迁到 [maestro-flow](https://github.com/catlog22/maestro-flow)，而后者**许可证未标注** |
| [Pimzino/claude-code-spec-workflow](https://github.com/Pimzino/claude-code-spec-workflow) | 已停滞一年多，仅支持 Claude Code，作者已转向 MCP 版 |
| [earthwalker17/agent-os](https://github.com/earthwalker17/agent-os) | 与 buildermethods 的同名项目**毫无关系**；仅 ~26★，个人项目，不要当底座 |

## 1. 前提：`AGENTS.md` 是唯一跨工具共识

这是整套方案的基石。你点名的三个工具，对指令文件的读取约定如下（均为官方来源核实）：

| 工具 | 读取约定 | 备注 |
|---|---|---|
| **Codex** | 根 `AGENTS.md` + 嵌套 `AGENTS.md` | AGENTS.md 规范最初就是 OpenAI Codex 牵头推动的 |
| **GitHub Copilot** | 根 `AGENTS.md` + 嵌套 `AGENTS.md`；同时兼容 `.github/copilot-instructions.md`、`.github/instructions/**.instructions.md`、`CLAUDE.md`、`GEMINI.md` | 官方 changelog 确认 coding agent 已支持 AGENTS.md |
| **Claude Code** | 默认 `claude-md-or-agents-md`：**仅当工作目录及以上不存在 `CLAUDE.md`/`CLAUDE.local.md` 时才读 `AGENTS.md`**（v2.1.277+）；可 `/config` 切成 `claude-md-and-agents-md` 同时读 | 最稳的写法是 `CLAUDE.md` 里写一行 `@AGENTS.md` 导入 |
| **DeepSeek Harness（当前环境）** | 原生加载 `$DSH_HOME/AGENTS.md` + 项目链 `AGENTS.md`/`CLAUDE.md` + `.local.md` 覆盖层；按 `.git` 定位项目根，从根到当前目录"由宽到专"排序，**内容重复的兄弟文件只渲染一次** | 已核实源码常量 |

### 推荐的文件布局（三工具通吃）

```
你的项目/
├── AGENTS.md                  # ← 唯一真相源，所有工具都读它
├── CLAUDE.md                  # ← 只有一行：@AGENTS.md
├── .github/
│   └── copilot-instructions.md  # ← 可选：只有一行，指向 AGENTS.md
├── packages/
│   └── app/
│       └── AGENTS.md          # ← 子目录专属规则（嵌套，就近优先）
└── .agents/skills/            # ← 跨工具 skill 目录（见第 5 节）
    └── <skill-name>/SKILL.md
```

`CLAUDE.md` 全文：

```markdown
@AGENTS.md
```

`.github/copilot-instructions.md` 全文：

```markdown
See AGENTS.md at the repository root for all project instructions.
```

> 为什么不反过来？因为 `AGENTS.md` 有官方规范（[agents.md](https://agents.md)，现由 Linux Foundation 下的 **Agentic AI Foundation** 托管，官方称 60k+ 项目在用），而 `CLAUDE.md` 是单厂商约定。让通用格式当真相源，厂商格式当适配层。

## 2. 四类项目对比

### A 类：规格驱动 / 计划驱动（解决"先想清楚再写"）

| 项目 | 是什么 | 规模 | 许可 | 最近更新 | 上手 |
|---|---|---|---|---|---|
| [github/spec-kit](https://github.com/github/spec-kit) | GitHub 官方 SDD 工具箱：结构化流程 + 模板 + 扩展机制 | ~141k★ | MIT | 2026-10-15 | `uv tool install specify-cli` → `specify init my-project --integration copilot` |
| [Fission-AI/OpenSpec](https://github.com/Fission-AI/OpenSpec) | 轻量 spec 层，自称 "fluid not rigid / built for brownfield" | ~72k★ | MIT | 2026-10-15 | `npm i -g @fission-ai/openspec@latest` → `openspec init` |
| [bmad-code-org/BMAD-METHOD](https://github.com/bmad-code-org/BMAD-METHOD) | 敏捷方法论 + 多角色 Agent 全流程体系 | ~54k★ | MIT(+商标) | 2026-10-16 | `npx bmad-method install`（v6.12）；v7 为 alpha，`npx skills add bmad-code-org/BMAD-METHOD` |
| [buildermethods/agent-os](https://github.com/buildermethods/agent-os) | 把代码库规范抽成 standards 再按需注入（不生成流程，管规范） | ~5.5k★ | MIT | 2026-10-07 | 官方安装页需留邮箱 → 未核实；仓库机制是 clone 后 `bash ~/agent-os/scripts/project-install.sh` |
| [eyaltoledano/claude-task-master](https://github.com/eyaltoledano/claude-task-master) | 任务台账：PRD → `tasks.json`，含依赖/优先级/复杂度 | ~28k★ | **MIT+Commons Clause** | 2026-04-28 | `npm i -g task-master-ai` → `task-master init` |
| [open-gsd/gsd-core](https://github.com/open-gsd/gsd-core) | Discuss→Plan→Execute→Verify→Ship 阶段循环，子 Agent 抗 context rot | ~10.6k★ | MIT | 2026-10-16 | `npx @opengsd/gsd-core@latest`（必须用安装器） |

**文件约定速记**
- spec-kit → `.specify/`，命令分发到 `.claude/skills`、`.github/skills`、`.agents/skills`、`.cursor/skills`；**已内置 `dsh` 集成**，支持 40+ 工具
- OpenSpec → `openspec/changes/<id>/{proposal,design,tasks}.md` + `openspec/specs/`；命令拼写随工具而变（Codex 是 `$openspec-propose`，Copilot/Cursor 是 `/opsx-propose`）
- BMAD v7 → `_bmad/`（共享运行时，定制放 `_bmad/custom/`）+ `_bmad-output`
- agent-os → `agent-os/standards/`、`agent-os/specs/<ts>-<slug>/`、`agent-os/product/`（注意**不是** `.agent-os/`）
- claude-task-master → `.taskmaster/`（但文档站与 README 对 `.taskmasterconfig` 位置说法不一致）

**怎么选**
- 想要**最轻、最好改** → OpenSpec。小坑：默认开匿名遥测，`openspec config set telemetry.enabled false` 关掉。
- 想要**官方背书 + 长期扩展性**（扩展/预设/工作流四层机制） → spec-kit。代价：多一套 Python 3.11 + uv 工具链，且流程偏重（constitution→specify→plan→tasks→implement→converge 多道关卡）。
- 只想**管规范不管流程** → agent-os，仓库小到可以直接读改（约 20 个文件）。

- **首选 `wshobson/agents`**：唯一做到"一份 Markdown 源 + 7 个 harness 各自安装路径"且带 CI 校验（`make validate STRICT=1`）的合集。体量大，**按 plugin 挑，不要全量注入**。

## 3. 分阶段落地路线（个人 → 团队）

每一阶段都有**明确的进入条件和退出条件**，避免一次装太多。

### 阶段 0：零框架跑通（1 天，成本≈0）

**做什么**
1. 在项目根写 `AGENTS.md`，先只写 5 件 agent 最常搞错的事（怎么构建、怎么跑测试、代码风格红线、别碰哪些目录、提交信息格式）。
2. 加 `CLAUDE.md`（内容 `@AGENTS.md`）和 `.github/copilot-instructions.md`（指向 AGENTS.md）。
3. 建 `.agents/skills/`，把你**重复交代过 3 次以上**的操作写成第一个 `SKILL.md`。

**退出条件**：在 Codex、Copilot、Claude Code 三个工具里各改一个真实任务，确认它们都遵守了同一份规则。

> 这一阶段刻意不装任何项目。因为你现在还不知道自己缺什么，装了也是照抄别人的流程。

### 阶段 1：加规格层（几天，卸装成本≈0）

**做什么（二选一）**
- 轻：`npm i -g @fission-ai/openspec@latest && openspec init`
- 重：`uv tool install specify-cli && specify init my-project --integration copilot`

**再加一层规范注入**：clone [buildermethods/agent-os](https://github.com/buildermethods/agent-os)，在你的项目里跑 `bash ~/agent-os/scripts/project-install.sh --profile default`，然后让 agent 用 `/discover-standards` 把你代码库里**已经存在但没写下来**的规范抽成 `agent-os/standards/`。

**退出条件**：连续 3 个需求都走了"先写 spec → 再写代码"，且你发现 agent 写错方向的次数明显下降。

> 为什么这个顺序？因为规格文件的价值来自"你反复被 agent 带偏"这个痛点。没痛点就写不出好 spec。

### 阶段 2：素材库 + 团队自动化

**做什么**
1. 从 [wshobson/agents](https://github.com/wshobson/agents) 里**只挑你技术栈对应的 1-2 个 plugin**（不要全量）。
2. 装 [obra/superpowers](https://github.com/obra/superpowers)，它的流程类 skill 改的是 agent 的工作方式，收益最直接。
3. 装 [anthropics/claude-code-action](https://github.com/anthropics/claude-code-action)，在 PR/issue 上触发——此时你的 `AGENTS.md`/`skills` 已经稳定，Action 只是**复用**它们。

**退出条件**：团队成员不需要口头交接，克隆仓库后 agent 就能按同一套规则干活。

### 阶段 3：按需上编排（可选，可能永远不需要）

只有当出现"一个任务需要多个 agent 并行/互审"或"需要定时/webhook 触发"的真实需求时才进入：
- 要**并行/互审** → 试 [ruvnet/ruflo](https://github.com/ruvnet/ruflo)，**按插件粒度渐进装**（先 `ruflo-core` + `ruflo-swarm`）。
- 要**常驻/定时/webhook** → 才上 [OpenHands](https://github.com/OpenHands/OpenHands) 自托管 Docker，并接受运维成本。
- 要**纯仓库内的 agentic 自动化** → [github/gh-aw](https://github.com/github/gh-aw)，注意版本安全公告。

## 4. 怎么迭代成"自己的"工作流

这才是你问题的核心。以上项目都只是起点，真正决定成败的是迭代纪律。

### 4.1 单一真相源原则（最重要）

你的工作流最终会有这些文件：`AGENTS.md`、`CLAUDE.md`、`skills/`、`standards/`、`openspec/`、各框架自己的目录……

**唯一不能违反的规则：同一个事实只写在一个地方，其他地方只引用。**

举例：
- ✅ `AGENTS.md` 写"测试命令是 `pnpm test`"，`skills/run-tests/SKILL.md` 说"见 AGENTS.md 的测试命令"
- ❌ `AGENTS.md` 和 `SKILL.md` 各写一遍测试命令 → 迟早不一致，agent 会随机选一个

同理，引入任何新框架前先问：**它能不能复用已有的 `AGENTS.md`/`skills`？** 不能就说明你在制造第二个真相源。

### 4.2 目录结构约定（建议固化下来）

```
项目/
├── AGENTS.md                    # 唯一真相源：全局规则
├── CLAUDE.md                    # @AGENTS.md
├── .github/copilot-instructions.md
├── .agents/skills/<name>/SKILL.md   # 你的自定义 skill（跨工具）
├── agent-os/standards/          # 从代码库抽出的规范（阶段 1 起）
├── openspec/                    # 变更提案与 spec（阶段 1 起）
│   ├── changes/<id>/
│   └── specs/
└── packages/*/AGENTS.md         # 子目录专属规则（就近优先）
```

> DSH 环境额外支持 `.dsh/skills/`（优先级高于 `.agents/skills/`）和 `~/.dsh/skills`；本项目里用 `.agents/skills/` 更通用。

### 4.3 用信号驱动迭代，而不是凭感觉加东西

每次迭代后记录这几个指标，只在下滑时动手：

| 信号 | 含义 | 对策 |
|---|---|---|
| agent 走错方向的次数 | spec 没写清 | 补 `AGENTS.md` 或 spec，而不是加更多 skill |
| 你重复解释同一件事 ≥3 次 | 该固化了 | 抽成一个 `SKILL.md` |
| 同一 skill 连续 5 次没被触发 | 描述写得不好，或它已无用 | 改 description 或删掉 |
| 多个文件对同一件事说法不同 | 真相源分裂 | 立即合并，删掉重复的 |
| skill 数量持续增长但任务没变快 | 上下文被噪声稀释 | 定期 prune |

**定期 prune 是必须的。** 素材库（wshobson、superpowers、ECC）动辄上百个 agent/skill，全量注入会稀释上下文、让 agent 表现变差。每季度删掉没用过的。

### 4.4 把你的工作流本身当代码管理

- `AGENTS.md`、`skills/`、`standards/` **全部进 git**，改动走 PR。
- 每个 skill 用 frontmatter 写 `name` + `description`，`description` 要写清**什么时候该用**（agent 靠它决定是否加载）。
- 改 `AGENTS.md` 时用 commit message 记下**触发这次修改的具体失败案例**。半年后你才知道哪条规则还有效。
- 想验证改动是否有效：把之前失败的任务重跑一遍，对比结果。这是唯一的客观标准。
