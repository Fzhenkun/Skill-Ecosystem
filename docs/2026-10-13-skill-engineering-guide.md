> 本文用于设计、创建、重构、验证和持续维护 Codex Skill。  
> 核心目标不是把更多说明塞进一个文件，而是让 Skill **被正确触发、按需加载、稳定执行、可安全恢复、持续改进**。

## 1. Skill 工程要解决的问题

一个可用的 Skill 至少要回答以下问题：

1. **什么时候必须触发？**
2. **什么时候不应该触发？**
3. **它具体能做什么，不能做什么？**
4. **需要哪些文件、工具、脚本或依赖？**
5. **Agent 应按什么顺序执行？**
6. **执行失败时应如何停止、诊断和恢复？**
7. **如何验证这次调用确实成功？**
8. **如何根据真实使用持续优化？**

如果只描述“这个 Skill 大概能做什么”，却没有触发边界、执行入口和失败处理，常见结果是：

- 该调用时没有调用；
- 不该调用时发生误触发；
- Agent 使用了错误的能力或错误的参数；
- 详细文档一次性全部进入上下文，浪费 Token；
- 脚本失败后 Agent 自行改脚本、换工具或猜测依赖，形成不可控的试错循环；
- 没有结构化证据，无法判断 Skill 是否真正被加载和执行。

因此，Skill 应被当作一个小型、可验证、可维护的软件包，而不是一段孤立的提示词。

### 1.1 从 Prompt 工程到 Skill 工程

项目级提示词适合承载全局规则，例如代码风格、目录约定和安全红线；Skill 适合封装可复用的领域知识和多步骤工作流。二者不是替代关系：全局提示词定义“这个项目的规矩”，Skill 定义“如何完成某一类任务”。

当所有知识都塞进全局提示词时，常见问题是上下文长期占用、不同任务相互干扰，以及工作流难以跨项目复用。Skill 的价值在于把知识和流程拆成可发现、可版本控制、按需加载的能力包。

### 1.2 渐进式披露的三阶段

Skill 的加载应至少区分三个阶段：

1. **发现（Discovery）**：会话启动时只提供 Skill 的名称和描述，用于判断是否匹配当前任务；
2. **激活（Activation）**：任务命中描述后读取完整 `SKILL.md`，获得路由表和全局约束；
3. **执行（Execution）**：按照路由按需读取参考文档、示例、脚本和资源。

这意味着“文件存在”不等于“内容已经加载”，而“`SKILL.md` 已加载”也不等于所有子模块都应被读取。每一层都应只承担当前阶段所需的上下文成本。

### 1.3 Skill 与全局提示词的边界

| 维度 | 全局提示词/项目规则 | Skill |
| --- | --- | --- |
| 主要职责 | 项目约定、通用规范和全局安全要求 | 特定领域知识和完整工作流 |
| 加载方式 | 通常随项目或会话常驻 | 命中任务后按需加载 |
| 生效范围 | 当前项目或当前环境 | 取决于 Skill 的安装作用域 |
| 组织方式 | 通常是单文件或扁平配置 | 主入口加模块、脚本和资源 |

如果某条规则对所有任务都适用，应放在全局规则中；如果只在某一类任务激活时适用，应放进 Skill，并在入口中明确其适用条件。

## 2. 标准 Skill 包结构

推荐的生产级目录结构如下：

```text
<skill-name>/
├── SKILL.md
├── agents/
│   └── openai.yaml
├── references/
│   ├── manifest.md
│   ├── workflow.md
│   ├── fallback.md
│   └── description-patterns.md
├── examples/
│   ├── positive.md
│   └── negative.md
├── scripts/
│   └── <deterministic-helper>.<ext>
└── assets/
    └── <template-or-bundled-file>
```

不是每个 Skill 都需要所有目录，但每个目录都必须有明确职责。最小结构通常是：

```text
<skill-name>/
├── SKILL.md
└── agents/
    └── openai.yaml
```

### 2.1 `SKILL.md`：唯一主入口

`SKILL.md` 负责：

- Skill 的名称和触发描述；
- 适用场景与非适用场景；
- 能力边界；
- 执行顺序；
- 按需读取哪些参考文件；
- 发生错误时必须读取哪个回退文档；
- 需要用户原文透传、结果透传或禁止改写的约束；
- 最终验证要求。

主文件应短而可执行。它不应包含完整 API 参数表、全部错误码、所有案例和大段背景知识。

### 2.2 `agents/openai.yaml`：代理元数据

用于承载 Skill 的界面或代理侧元数据。名称、描述和入口应与 `SKILL.md` 保持一致，避免出现：

- 文件名与元数据名称不一致；
- 元数据仍指向已经删除的参考文件；
- 用户看到的描述与实际触发范围不一致。

### 2.3 `references/`：按需加载的详细知识

建议使用以下职责划分：

| 文件 | 解决的问题 |
| --- | --- |
| `manifest.md` | Skill 的完整能力清单、输入输出、边界和依赖 |
| `workflow.md` | 创建、调用、验证和维护的详细流程 |
| `fallback.md` | 命令失败、依赖缺失、格式错误和权限问题的处理协议 |
| `description-patterns.md` | 描述和触发词的编写模式、反例和优化规则 |

只有在当前任务需要时才读取对应文件。不要为了“保险”一次性读取整个 `references/`。

> `agents/openai.yaml` 等元数据文件属于宿主平台的可选适配层，不应被误写成所有 Agent 都必须支持的通用协议。使用前应确认目标平台的文件名、字段和加载方式，并确保它们与 `SKILL.md` 保持一致。

### 2.4 `examples/`：正向和反向用例

至少应包含：

- 正向用例：哪些请求应该触发，以及期望的执行方式；
- 反向用例：哪些相似请求不应触发，以及应由什么能力处理。

用例不是装饰性文档。它们用于校准触发边界、发现描述歧义和验证结果是否符合预期。

### 2.5 `scripts/`：确定性执行入口

当某个动作需要重复执行、参数容易漏传或步骤容易漂移时，应使用脚本封装。适合脚本化的内容包括：

- 目录结构检查；
- 固定格式转换；
- 日志解析；
- 数据采集和去重；
- 回归验证；
- 依赖和缓存版本检查。

脚本应尽量提供一个清晰、可复制的入口命令，而不是要求 Agent 手工拼接一长串命令。

### 2.6 `assets/`：模板和打包资源

只有在 Skill 确实需要模板、配置样例、固定资源或其他随 Skill 分发的文件时才创建。不要把临时输出或运行日志放入该目录。

## 3. 命名和元数据规则

### 3.1 Skill 名称

Skill 目录名应使用小写、连字符分隔的形式，并控制在 64 个字符以内：

```text
skill-lifecycle-engine
review-agent
image-generation
```

避免使用空格、混合大小写、过长名称和含义不明确的缩写。

### 3.2 Description 的组成

高质量描述至少包含五类信息：

1. **能力**：这个 Skill 做什么；
2. **触发场景**：用户提出哪些具体任务时必须使用；
3. **高信号关键词**：术语、缩写、文件名、协议名和英文别名；
4. **反向排除**：哪些相似任务不应使用；
5. **双语覆盖**：中英文环境下都可能出现的触发词。

推荐使用如下结构：

```yaml
description: |
  Use this skill when ...
  It must be used for ...
  Trigger phrases include: ...
  Do not use it for ...
```

Description 应优先列举真实任务，而不是使用“帮助完成相关工作”这类泛化表述。长度应以信息密度为准，避免为了达到固定字数而填充重复句子。

> 不同宿主平台可能对 `name`、`description` 以外的 frontmatter 字段提供额外支持，例如参数提示、工具白名单或手动/自动调用控制。这些字段只能在目标平台已验证时使用；跨平台 Skill 应把平台差异放入适配层，不能把某个平台的字段当作开放格式的必填项。

### 3.3 触发场景表

当 Skill 支持多个场景时，优先使用结构化表格：

| 场景 | 典型用户请求 | 高信号触发词 |
| --- | --- | --- |
| 创建新 Skill | “为日志解析创建一个完整 Skill” | 创建技能、创建 Skill、create skill、scaffold |
| 补全已有 Skill | “补上这个 Skill 缺失的 references 和脚本” | 补全技能、修复 Skill、complete skill、repair |
| 优化触发 | “让这个 Skill 更准确地触发” | 触发优化、描述优化、trigger、frontmatter |
| 拆分大文件 | “把这个过大的 SKILL.md 拆成按需引用文档” | 渐进式披露、拆分文档、progressive disclosure |
| 建立维护流程 | “为这个 Skill 加验证和持续维护机制” | 维护技能、技能工作流、maintain skill |

触发词应服务于实际路由，不应把所有宽泛的领域词都堆进去。越宽泛的词越容易造成误触发。

### 3.4 作用域与优先级

Skill 的作用域决定它在哪些任务中可见。常见的作用域包括企业级配置、用户级配置、项目级目录和 Plugin 内置资源。它们的具体名称和优先级由宿主平台决定，不能仅凭目录位置推断。

在需要同时存在多个 Skill 时，应记录以下信息：

- Skill 的安装作用域和生效范围；
- 是否允许模型自动调用，还是只能由用户显式调用；
- 与其他 Skill 的触发重叠和排除规则；
- 冲突时采用的平台优先级，以及无法判断时的停止策略。

> 常见的优先级模型是“企业策略 > 用户配置 > 项目配置 > Plugin 内置”，但这只是待平台验证的默认假设。文档和测试应以实际宿主行为为准。

## 4. 渐进式披露

### 4.1 分层加载模型

推荐采用三层内容模型：

```text
触发层：SKILL.md
  -> 判断是否使用、读取哪个参考文件、先做什么

执行层：references/workflow.md、manifest.md、fallback.md
  -> 获取当前子任务所需的详细规则

工具层：scripts/、assets/、examples/
  -> 执行确定性动作、读取模板、参考正反案例
```

每次调用只加载当前任务需要的内容：

| 当前需要 | 首选读取 |
| --- | --- |
| 判断能力范围 | `references/manifest.md` |
| 执行完整流程 | `references/workflow.md` |
| 处理命令或依赖失败 | `references/fallback.md` |
| 优化触发描述 | `references/description-patterns.md` |
| 判断正反触发边界 | `examples/positive.md`、`examples/negative.md` |

### 4.2 不应放进主文件的内容

以下内容通常应拆出：

- 完整 API 参数说明；
- 大型错误码表；
- 长篇背景介绍；
- 大量正反案例；
- 某个平台的完整日志样本；
- 与当前任务无关的实现细节；
- 只在排错时需要的诊断命令。

主文件只保留“何时读取这些内容”的路由信息。

### 4.3 路由必须显式

不要只创建参考文件而不在 `SKILL.md` 中指向它们。路由应明确说明：

- 需要了解完整能力时读取哪个文件；
- 需要执行流程时读取哪个文件；
- 出现错误时必须读取哪个文件；
- 需要判断触发边界时读取哪些示例。

## 5. 输入、输出与用户原文保真

当 Skill 将用户内容传给脚本、API 或外部服务时，应明确区分三种信息：

1. **控制参数**：Skill 为了执行任务而生成的结构化参数；
2. **用户原文**：用户明确提供的需求、代码、URL、路径、名称和筛选条件；
3. **系统元数据**：运行时生成的时间戳、会话 ID、版本和日志信息。

### 5.1 原文保真原则

除非用户明确要求改写，否则：

- 不翻译、不缩写、不润色用户提供的代码和标识符；
- 不修改表名、列名、用户 ID、URL、文件路径和时间表达；
- 用户问题中包含的 SQL、JSON、命令或配置应完整传递；
- 结构化参数应保留用户原文，必要时另设解释字段；
- 不使用 Agent 的“合理推断”替换用户没有提供的值。

### 5.2 结果透传原则

如果 Skill 的职责是调用底层服务或执行诊断，默认应：

- 保留原始成功或失败状态；
- 呈现关键原始输出；
- 不擅自过滤、修正或伪造结果；
- 对新增解释与底层结果明确区分。

如果业务确实需要清洗、聚合或脱敏，应把规则写成显式步骤，并定义可验证的输入输出。

## 6. 执行入口和工作流

### 6.1 入口收敛

重复执行的工作应尽量收敛到一个命令或一个脚本入口：

```powershell
python scripts/maintain_skill.py --skill-dir <path-to-skill>
```

理想的入口应满足：

- 参数显式；
- 路径可检查；
- 依赖集中管理；
- 鉴权在受控脚本内处理；
- 输出状态明确；
- 失败时返回非零退出码；
- 可以被回归测试和 CI 重复执行。

### 6.2 推荐执行顺序

1. 读取当前任务相关的 `SKILL.md` 路由；
2. 判断当前请求是否属于 Skill 的适用范围；
3. 读取本次子任务所需的一个或多个参考文件；
4. 保留用户原文和关键上下文；
5. 检查路径、依赖、权限和输入格式；
6. 执行唯一入口命令或确定性工具；
7. 检查退出码、输出结构和副作用；
8. 根据验证结果继续、修复或进入回退协议；
9. 汇报结果、证据和剩余风险。

### 6.3 依赖和鉴权

依赖应尽量由项目或脚本自带、固定版本或明确声明。Agent 不应：

- 在没有证据时安装随机依赖；
- 复制其他 Skill 的鉴权逻辑；
- 让用户把 Cookie、Token 或密钥直接放入聊天内容；
- 把临时凭据硬编码进脚本或文档。

### 6.4 工具白名单与模块隔离

当一个 Skill 包含多个模块或多个外部接口时，应按模块建立工具白名单，而不是让所有模块共享一组“万能工具”。每个模块至少应说明：

- 允许调用的工具和接口；
- 明确禁止调用的高风险或易混淆接口；
- 工具不可用时的回退动作；
- 工具调用产生的副作用和验证方式。

> 直接 HTTP 调用、任意命令执行和审批/发布类接口等高风险能力，除非有明确授权和隔离设计，否则不应作为通用兜底。权限最小化的目标是让 Agent 即使误解当前子任务，也无法调用超出模块职责的能力。

### 6.5 跨阶段参数与快照

多步骤 Skill 不应依赖 Agent 在上下文中“记住”所有中间参数。需要跨阶段传递的关键参数可以写入结构化快照，并在每个阶段设置门卡校验：

```text
用户输入/动态查询
  -> 参数标准化
  -> 快照写入
  -> 阶段校验
  -> 下一阶段读取
```

> 快照应满足：来源和去向可追溯、字段完整性可校验、关键值不会在阶段切换时丢失、重复执行不会覆盖无关配置。用户直接提供的值、动态查询得到的值和系统生成的元数据应分开记录，避免把推断值伪装成用户输入。

## 7. 错误熔断和回退协议

错误处理不是附录，而是 Skill 的核心能力。任何命令、脚本、依赖检查或验证步骤失败时，应立即进入回退流程。

### 7.1 首次失败规则

出现以下任一情况时，必须优先读取 `references/fallback.md`：

- 命令返回非零退出码；
- 脚本崩溃或输出格式异常；
- 依赖缺失或版本不匹配；
- 路径不存在或权限不足；
- 输入文件无法解析；
- 校验失败；
- 运行结果与预期结构不一致。

### 7.2 Agent 端禁止行为

在读取并执行回退协议前，禁止：

- 随意修改本地脚本；
- 擅自更换工具或执行入口；
- 安装没有证据支持的依赖；
- 跨 Skill 复制认证逻辑；
- 猜测参数并重复试错；
- 降级到不安全的鉴权或文件操作方案；
- 删除缓存、日志或用户文件来掩盖失败；
- 把未验证的猜测当成成功结果。

### 7.3 最小恢复流程

1. 记录准确的失败命令、路径、退出码和关键错误文本；
2. 判断失败属于结构、环境、依赖、权限还是内容问题；
3. 读取 `fallback.md`，匹配对应的处理分支；
4. 只执行文档明确允许的最小修复；
5. 重新执行原命令；
6. 通过验证后再继续；
7. 若需要用户或外部状态介入，停止猜测并给出可复制的修复指令。

### 7.4 面向用户的恢复话术

需要用户介入时，应包含：

1. 具体问题；
2. 影响范围；
3. 精确的修复动作或命令；
4. 完成后的验证方式；
5. 用户应如何反馈。

示例：

```text
验证失败：SKILL.md 缺少有效的 YAML frontmatter，当前无法判断 Skill 名称和描述。
请补充 name 和 description 字段，然后重新执行验证命令。
完成后请回复：已修复
```

## 8. 验证和质量门槛

Skill 完成后至少验证以下内容：

### 8.1 结构验证

- 目录名符合小写连字符规则；
- `SKILL.md` 存在且可解析；
- YAML frontmatter 有效；
- `name`、`description` 和实际目录一致；
- `agents/openai.yaml` 存在或有明确理由不需要；
- `SKILL.md` 引用的文件真实存在；
- 没有指向旧路径、旧文件名或不存在的脚本。

### 8.2 触发验证

- 正向请求能够触发；
- 相似但不相关的请求不会误触发；
- 中英文关键词都覆盖真实表达；
- 高信号术语优先于宽泛领域词；
- 反向排除规则明确。

### 8.3 执行验证

- 入口命令可以复制执行；
- 参数缺失时能给出清晰错误；
- 正常流程返回可验证结果；
- 失败流程进入 fallback，而不是无限试错；
- 脚本不会修改无关文件；
- 路径、编码、权限和依赖问题有明确处理。

### 8.4 结果验证

- 结果与底层输出一致；
- 用户原文中的关键标识没有丢失；
- 日志、缓存和去重逻辑有版本管理；
- 统计结果可以通过独立样本或回归测试复核；
- 结论与证据范围一致，不把一次实测泛化为所有平台规则。

### 8.5 三类回归测试

复杂 Skill 至少应覆盖三类测试：

1. **触发测试**：准备约 10 个真实语气和表达方式的正向变体，同时准备相似但不相关的反向样例；
2. **功能走查**：用自然语言跑通完整流程，覆盖路由、按需加载、工具红线、边界输入和异常回退；
3. **性能对比**：对同一任务比较“无 Skill”和“有 Skill”的多次运行，记录上下文成本、完成质量、耗时和失败率。

测试不应只覆盖成功路径。至少要故意检查边界值、依赖不可用、参数缺失、禁止工具调用和未知日志事件，并把测试样本与预期结果纳入版本控制。

## 9. 维护闭环

Skill 应采用“小范围、可验证”的持续维护方式：

```text
真实使用
  -> 记录问题
  -> 分类问题
  -> 修改最小必要文件
  -> 重新验证
  -> 记录验证结果
```

### 9.1 问题分类与修改位置

| 问题 | 优先修改 |
| --- | --- |
| 应触发却未触发 | `SKILL.md` 的 description、关键词或场景表 |
| 不应触发却误触发 | `SKILL.md` 的排除规则和反向示例 |
| 主文件过长 | 将细节移动到 `references/` |
| 反复手工操作 | 增加或改进 `scripts/` |
| Agent 误解用法 | 增加正向或反向 `examples/` |
| 报错后行为失控 | 补强 `references/fallback.md` |
| 能力边界不清 | 更新 `references/manifest.md` |
| 流程步骤不一致 | 更新 `references/workflow.md` |

不要因为一次问题就整体重写 Skill。优先定位触发层、知识层、工具层或验证层中的最小责任文件。

### 9.2 版本化和缓存

如果 Skill 的输出会被缓存或用于统计，应记录：

- Skill 版本；
- 解析器或 collector 版本；
- 输入日志格式；
- 缓存格式版本；
- 去重规则；
- 验证样本和预期结果。

当解析逻辑发生不兼容变化时，应升级缓存版本或清晰地使旧缓存失效，避免新旧数据混合。

## 10. 平台调用记录的验证案例

本节只描述一次实际采集工作中观察到的证据，不应被当作所有 Codex、Copilot 或未来版本的永久协议。平台日志格式发生变化时，必须以当前真实日志和官方文档为准。

### 10.1 验证思路

验证一个 Skill 是否被调用，至少需要区分三个阶段：

1. **发现**：运行时找到 Skill 及其 `SKILL.md`；
2. **调用**：产生明确的 Skill 调用事件；
3. **交付**：Skill 上下文被交付给模型。

仅凭目录存在、工具已安装或某个关键词出现在普通文本中，不能证明 Skill 已被调用。

### 10.2 Codex 实测信号

在本次实测日志中，较可信的判断依据包括：

- 会话日志位于用户目录下的 `.codex/sessions`；
- 日志事件的 `content_item_kinds` 包含 `skills.selected_skill_instructions`；
- 注入内容中包含 Skill 名称、路径和 `SKILL.md` 内容。

因此，统计 Codex Skill 调用时，应优先解析结构化会话事件，而不是依赖命令名、进程名或旧安装目录猜测。

### 10.3 GitHub Copilot 实测信号

在本次实测日志中，观察到的可信信号包括：

- 会话状态位于用户目录下的 `.copilot/session-state`；
- 日志包含顶层 `type: "skill.invoked"`；
- `data.name`、`data.path` 等字段提供 Skill 名称和 `SKILL.md` 路径；
- 另有上下文交付事件，用于说明 Skill 内容已交给模型。

这些字段属于本次环境和日志版本中的观察结果。解析器应保留事件版本兼容策略，并对未知事件安全跳过、记录诊断信息。

### 10.4 统计链路的推荐设计

一个稳健的 collector 应分成以下步骤：

1. 检查实际会话目录，而不是只检查历史安装痕迹；
2. 扫描结构化日志；
3. 识别明确的 Skill 调用事件；
4. 提取名称、路径、时间、工具、模型和会话信息；
5. 使用稳定事件 ID 或组合键去重；
6. 将原始记录与去重结果分开保存；
7. 为解析逻辑维护缓存版本；
8. 使用真实样本和回归测试验证；
9. 对未知日志格式返回诊断，而不是静默生成错误统计。

## 11. 反模式清单

以下做法会降低 Skill 的可靠性：

1. 用 `skills.md`、`inference/` 等自定义名称替代平台约定，却没有兼容层或明确理由；
2. 把完整说明书全部塞进 `SKILL.md`；
3. 只写“适用于自动化任务”这类宽泛描述；
4. 只列正向触发词，不写排除场景；
5. 让 Agent 手工执行多个易错命令；
6. 发生错误后允许 Agent 自行改脚本、换工具和安装依赖；
7. 将用户提供的路径、URL、代码或标识符改写成“更合理”的形式；
8. 用目录存在或工具安装状态冒充 Skill 调用证据；
9. 只展示成功样例，不准备失败样例；
10. 修改后不重新做结构、触发、执行和结果验证；
11. 把单个平台、单个版本的日志字段写成永久通用协议；
12. 将临时日志、缓存和测试输出混入 Skill 的正式结构。

## 12. 交付检查表

提交一个新的或更新后的 Skill 前，逐项检查：

- [ ] Skill 名称为小写连字符格式，且不超过 64 个字符；
- [ ] `SKILL.md` 具有清晰、具体、可路由的描述；
- [ ] 描述包含正向场景、关键词和反向排除；
- [ ] `SKILL.md` 只保留路由和操作规则；
- [ ] 详细能力说明已放入 `references/`；
- [ ] `references/fallback.md` 定义了失败后的熔断与恢复；
- [ ] 脚本入口已收敛，且命令可以复制执行；
- [ ] 有正向和反向示例；
- [ ] 所有引用路径都真实存在；
- [ ] 已完成结构验证；
- [ ] 已完成正向和反向触发验证；
- [ ] 已完成成功和失败执行验证；
- [ ] 用户原文、关键路径和标识符能够保真传递；
- [ ] 日志、缓存和统计逻辑有版本或兼容策略；
- [ ] 已记录验证结果和剩余风险。

## 结论

高质量 Skill 的关键不在于文档写得多，而在于边界清晰、路由准确、内容按需加载、执行入口稳定、失败行为受控，并且能够从真实使用中持续校正。

可以将完整方法概括为：

```text
强触发描述
  + 清晰能力边界
  + 渐进式披露
  + 单一执行入口
  + 作用域与工具隔离
  + 用户原文保真
  + 跨阶段参数可追溯
  + 错误熔断协议
  + 正反向示例
  + 结构化验证
  + 持续维护闭环
```
