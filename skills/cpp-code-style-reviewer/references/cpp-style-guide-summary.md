# C++ 规范总览与调查笔记

本文根据参考图片 `D:\projects\Personal_blog_website\input.png` 中的 Google C++ Style Guide 批注整理，目标是帮助审查者先理解整体系统，再处理单条规则。它是工程规范摘要，不替代项目自己的 `.clang-format`、`clang-tidy`、编译器约束或代码所有权规则。

## 一、全局地图：规范到底在解决什么

C++ 风格规范的核心不是“把代码排得好看”，而是降低多人协作中三类成本：

1. **阅读成本**：让读者能快速找到接口、状态、控制流和资源所有权。
2. **误用成本**：限制隐式转换、宏污染、未定义行为和模糊的生命周期。
3. **变更成本**：让 diff 稳定、头文件依赖可追踪、格式和命名可预测。

可以把规则分成四层，审查时按这个顺序定位：

| 层次 | 主要问题 | 代表规则 |
| --- | --- | --- |
| 可编译性与边界 | 文件能否独立理解，依赖是否明确 | include、自包含、头文件保护、命名空间 |
| 语义安全 | 代码是否可能被误用或产生隐式行为 | `explicit`、`const`、`nullptr`、命名转换、RAII |
| 协作可读性 | 不同作者能否快速扫描和比较 diff | 缩进、空格、行宽、括号、成员顺序 |
| 长期维护 | 代码是否能在演进中保持稳定 | 命名、宏限制、接口边界、默认规则和例外 |

### 规范之间的优先级

1. 语言规则、未定义行为和安全约束。
2. 项目级约定和构建工具配置。
3. 团队采用的 Google C++ Style Guide 子集。
4. 本文的通用建议。

冲突时不要机械地说“Google 风格一定正确”。应记录项目规则、通用规则和选择理由。规范的价值来自一致性，而不是来自某个品牌名称。

## 二、关键部分详解

### 1. 文件头、许可证和头文件自包含

**怎么用**

- 新文件使用项目规定的版权和许可证模板。
- 头文件只依赖自己直接使用的声明，不依赖“碰巧被其他头文件带进来”的类型。
- 源文件通常先 include 自己对应的头文件，再按 C 系统头、C++ 标准库、第三方库、项目头文件分组排序；具体顺序服从项目配置。

**为什么重要**

头文件是依赖边界。一个头文件能够独立编译，才能尽早暴露缺失 include、循环依赖和隐藏耦合。排序的主要作用是稳定 diff，并尽量让“自包含失败”在当前文件暴露。

**边界和问题**

- 预编译头、模块系统和生成代码可能有自己的顺序，不能直接套用普通源文件规则。
- 许可证文本不是格式化内容，自动工具不应替换或重写。
- include 排序只能做机械初筛，宏条件和平台分支通常需要人工确认。

**历史追溯**

“先包含自己的头文件”是对历史上隐式依赖问题的工程回应：当公共头文件变化时，原本被间接包含的声明可能消失，导致远处文件突然失败。这个规则看似严格，实际是在缩短故障定位路径。

### 2. Include guard 与 `#pragma once`

**怎么用**

```cpp
#ifndef PROJECT_NET_HTTP_CLIENT_H_
#define PROJECT_NET_HTTP_CLIENT_H_

// declarations

#endif  // PROJECT_NET_HTTP_CLIENT_H_
```

项目明确统一使用 `#pragma once` 时，按项目规则执行；不要在同一项目中随意混用。

**核心机制**

头文件可能被多个翻译单元或多次间接包含。保护宏让预处理器只展开一次，避免重复定义。

**边界和不足**

- 宏名必须足够唯一，否则两个文件可能意外共享保护宏。
- `#pragma once` 在现代编译器中普遍可用，但历史工具链、网络文件系统和特殊路径曾存在兼容性问题。

**历史追溯**

保护宏是 C/C++ 传统预处理模型下的可移植方案；`#pragma once` 是编译器长期提供的便利扩展。规范要求统一，主要是为了避免工具链差异和团队风格分裂。

### 3. 缩进、空格、括号和行宽

**怎么用**

- 使用 2 个空格缩进，不使用 tab。
- 控制语句与括号之间留空格：`if (ready)`。
- 函数调用括号不额外加空格：`Run()`。
- 运算符、逗号和注释保持稳定间距。
- `else` 与前一个 `}` 同行；复杂条件和长参数列表换行。
- 80 列是默认审查提示，不是对 URL、长字符串、许可证行的绝对禁令。

**核心机制**

固定格式让读者把注意力放在语义差异，而不是作者个人排版差异。稳定的换行也让版本控制 diff 更小、更容易审查。

**边界和不足**

- 纯人工格式化容易漂移，应优先使用项目的 `clang-format`。
- 行宽是可读性启发式；表格、错误消息、模板和生成代码可能合理超长。
- 格式化工具不理解所有业务语义，执行前要检查宏、字符串和注释。

**历史追溯**

80 列与早期终端、打印纸、并排 diff 的显示限制有关。今天屏幕更宽，但窄行仍有利于代码审查、分屏阅读和移动端查看，因此它保留为协作约束，而非机器硬限制。

### 4. 命名

**怎么用**

| 对象 | 常见形式 | 例子 |
| --- | --- | --- |
| 类型、类、枚举 | PascalCase | `HttpClient` |
| 函数、变量、命名空间、文件 | snake_case | `read_buffer` |
| 常量 | `kPascalCase` 或项目约定 | `kMaxRetries` |
| 宏 | `UPPER_SNAKE_CASE` | `PROJECT_FEATURE_FLAG` |

命名应表达职责、单位和所有权。布尔值优先使用 `is_`、`has_`、`can_` 等能读成问题的名称。

**适用边界**

- 外部 ABI、协议字段、第三方 API 和历史公共接口可能必须保留旧命名。
- 缩写只有在团队普遍理解时才适合使用；不要为了形式把名称缩短到失去语义。
- 命名变更可能影响序列化、反射、脚本绑定和 ABI，不能作为机械修正。

### 5. 命名空间和 `using`

**怎么用**

```cpp
namespace project::net {
class HttpClient {};
}  // namespace project::net
```

避免在头文件写 `using namespace std;`。需要少量名称时使用限定名或局部 `using std::string;`。

**核心机制**

未限定名称会扩大查找集合。头文件中的 using 指令会把名称污染传播给所有包含者，造成歧义和不稳定的重载解析。

**边界和不足**

- 匿名命名空间适合源文件内部链接，但不要用它替代清晰的模块边界。
- 在单个函数内部的局部 using 声明风险较低，但仍应考虑可读性。

### 6. 类、构造函数、`const` 和 `override`

**怎么用**

```cpp
class Buffer {
 public:
  explicit Buffer(size_t capacity);
  size_t size() const;
  void Clear() override;
};
```

- 成员按 `public`、`protected`、`private` 分组，并保持顺序稳定。
- 单参数构造函数默认考虑 `explicit`。
- 不修改对象状态的成员函数加 `const`。
- 重写虚函数使用 `override`，让编译器检查签名是否真的匹配。

**核心机制**

`explicit` 关闭不期望的隐式转换；`const` 把“不修改状态”变成可检查的接口承诺；`override` 把继承关系中的拼写或签名错误交给编译器发现。

**边界和问题**

- `explicit` 可能阻止原本有意的隐式构造，需要检查调用点。
- `const` 不是线程安全保证，也不能阻止 `mutable` 或间接修改外部状态。
- `override` 只能检查继承签名，不能证明实现逻辑正确。
- 三五法则/零法则要结合资源管理设计，不能仅凭风格规则添加析构、拷贝或移动函数。

### 7. 指针、引用和资源所有权

**怎么用**

```cpp
void SetName(const std::string& name);
std::unique_ptr<Worker> worker;
int* nullable_view = nullptr;
```

声明符靠近类型一侧，优先引用表达非空借用，使用智能指针表达拥有关系，使用 RAII 管理锁、文件、内存和句柄。

**核心机制**

类型和声明符共同决定声明含义；所有权明确后，释放时机由对象生命周期而不是调用者记忆决定。

**适用边界**

- C API、观察指针、对象池和跨 ABI 接口可能需要裸指针。
- `std::unique_ptr` 表达独占所有权，`std::shared_ptr` 表达共享生命周期；后者会引入引用计数、循环引用和性能成本。
- 引用不能表达空值；可能为空时应使用指针、optional 或明确的状态类型。

### 8. 现代 C++ 替代旧写法

| 旧写法 | 优先选择 | 需要注意 |
| --- | --- | --- |
| `NULL`、指针位置的 `0` | `nullptr` | 重载解析可能改变，需编译验证 |
| C 风格转换 | `static_cast` 等命名转换 | 明确转换意图，不代表转换一定安全 |
| 宏常量/宏函数 | `constexpr`、函数、模板 | 预处理器条件编译仍可使用宏 |
| 手写资源释放 | RAII、标准容器、智能指针 | 需先厘清所有权 |
| 索引循环 | 范围 for、算法 | 需要索引时不要为了形式强行改写 |

这些替代方案的共同目标是让编译器看到更多意图，并减少预处理器和隐式规则带来的隐藏行为。

### 9. 控制流、返回值和宏

**怎么用**

- `switch` 明确处理 `default`，或在项目规范允许时明确说明为何不需要。
- 返回表达式避免无意义括号，但宏参数、优先级和复杂表达式要优先保证语义清楚。
- 宏只用于条件编译、平台适配或确有必要的预处理器能力；不要用宏模拟普通常量、函数和复杂逻辑。

**常见问题**

- `default` 可能掩盖新增枚举值；对穷举枚举的项目应采用编译器告警策略。
- 宏没有类型、作用域和正常调试边界，参数还可能被重复求值。
- “符合格式”不等于控制流正确，仍需编译器、静态分析和测试验证。

## 三、调查与实践顺序

面对一个新 C++ 项目，先做全局扫描：目录、构建系统、编译器版本、`.clang-format`、`clang-tidy`、第三方库、生成代码和公共接口。然后选三个抓手深入：

1. 一个公共头文件：检查自包含、include guard、依赖层次和命名空间。
2. 一个资源管理类：检查构造、析构、拷贝/移动、所有权、`const` 和异常安全。
3. 一个复杂控制流函数：检查命名、缩进、边界条件、转换和返回值。

对“不符合常理”的地方追溯历史：查 git blame、引入提交、兼容性注释、旧编译器约束和 ABI/协议要求。确认它是遗留债务、外部约束还是有意例外，再决定是否修改。

## 四、最小审查清单

- [ ] 项目规则是否覆盖或改变了 Google 风格？
- [ ] 头文件是否可独立理解？include 是否直接、稳定、无重复？
- [ ] 所有权和空值语义是否明确？
- [ ] 是否存在隐式转换、C 风格转换、`NULL` 或危险宏？
- [ ] 类接口是否使用 `explicit`、`const`、`override`？
- [ ] 命名是否表达职责、单位和生命周期？
- [ ] 格式化是否稳定，长行是否有合理例外？
- [ ] 规则例外是否有历史原因或兼容性依据？
- [ ] 建议是否区分可自动修正和必须人工确认？

## 五、结论

高质量 C++ 规范审查应先确认项目的依赖和历史，再对关键接口和资源生命周期做语义分析，最后才处理格式细节。格式工具适合消除机械差异；代码审查的核心仍是依赖边界、隐式行为、所有权和接口可维护性。
