# Workflow

## 1. 明确任务边界

先确认或从用户请求中提取：

| 项目 | 要记录的内容 |
|---|---|
| 输入 | 参考文档、待整理目录、单独文件 |
| 输出 | 文件路径、文件名、是否需要博客化 |
| 目标 | 面试、考试、学习、项目落地、能力提升 |
| 期限 | 日期、天数、每周可投入时间 |
| 基线 | 已掌握内容、薄弱项、可用工具 |
| 限制 | 不改原文、语言、格式、题数、时间、是否需要代码 |

用户没有提供某项时，采用保守默认值，并在指南开头说明假设。

## 2. 读取和盘点材料

不要只看文件名。至少提取：

- 文件标题和标题层级；
- 题目、章节或主题清单；
- 每个主题的思路、模板、复杂度、易错点；
- 重复内容和相互依赖；
- 材料缺口与可能需要补充的领域知识。

目录任务要递归查找全部 `.md` 文件。对于内容较长的文件，先抽取结构，再按主题阅读完整内容；最终索引必须覆盖每个源文件。

推荐输出内部盘点表：

| 文件 | 主题 | 核心方法 | 代表内容 | 依赖 | 缺口 |
|---|---|---|---|---|---|
| `示例.md` | 双指针 | 首尾夹逼 | 题目 A、B | 排序 | 边界总结不足 |

## 3. 内容综合原则

按“问题信号 → 模型/模板 → 不变量或状态 → 代表任务 → 易错点 → 验收方式”重组材料。

每个领域至少回答：

1. 看到什么条件应该想到这个主题？
2. 该方法解决的核心矛盾是什么？
3. 执行时必须保持什么不变量？
4. 哪些边界或错误最常见？
5. 怎样证明已经掌握，而不是只看懂了？

材料之间存在重复时，保留最清晰的解释并合并代表任务。材料存在差异时，优先尊重用户指定的参考文档，并在必要时标记“实现相关”或“需要按题目约束判断”。

## 4. 设计 SMART 目标

### S：具体

不要写“提高能力”。写成“掌握哪些主题、能执行什么动作、产生什么输出”。

示例：

> 掌握数组、链表、哈希、双指针、树和 DP 六条主线；每条主线完成模板题、变式题和一次限时复写。

### M：可度量

优先使用：

- 独立完成题数；
- 规定时间内完成率；
- 正确率或通过率；
- 能否脱稿讲出定义、原理/不变量、场景、坑点；
- 错题复写次数；
- 随机抽题的稳定性。

### A：可实现

按单次学习时段拆解，每项任务应能在 30～120 分钟内完成。避免第一轮同时追求“全覆盖、全背诵、全部高难度、零错误”。

### R：相关

说明内容如何服务用户目标，例如面试手撕、项目稳定性、考试题型、工作流程或实际交付。低相关内容只能放在 P2 或扩展阅读。

### T：有期限

至少给出：

- 首轮完成时间；
- 错题/问题复写间隔；
- 阶段检查点；
- 截止日前的冲刺/速记安排。

## 5. 划分优先级

默认使用：

- P0：高频、高收益、强依赖，未掌握会阻塞后续；
- P1：常见进阶，能体现综合能力；
- P2：补充深度、低频追问或扩展内容。

优先级判断依据：

1. 与目标的相关性；
2. 在材料中的出现频率；
3. 对后续主题的依赖程度；
4. 失败成本；
5. 学会后能覆盖多少变式。

## 6. 设计执行单元

每个执行单元至少包含：

| 字段 | 含义 |
|---|---|
| 重点 | 本次真正要解决的一个主题 |
| 输入 | 要阅读/练习的源文件或题目 |
| 动作 | 复述、推导、编码、演练、复写、模拟 |
| 输出 | 笔记、代码、口述答案、错题记录或测试结果 |
| 时间盒 | 预计用时和截止时间 |
| 验收 | 如何判断完成 |
| 下一步 | 若完成或未完成分别做什么 |

## 7. 面试/实践类任务的固定节奏

对于编程手撕等需要现场表现的任务，建议使用：

1. 读约束；
2. 说暴力方案和瓶颈；
3. 识别优化模型；
4. 说不变量/状态；
5. 编码；
6. 边界自测；
7. 报复杂度；
8. 复盘错误。

其他领域可将这套流程替换为对应的“理解 → 练习 → 输出 → 检查 → 复盘”流程，不要机械保留无关内容。

## 8. 进度和复盘设计

至少生成三张表：

### 每日表

记录日期、主题、具体任务、完成度、当前 P0 重点、卡点、结论和下一步动作。

### 单项表

记录任务名称、类型、独立用时、是否完成、是否看提示、关键方法、错误原因和复查日期。

### 周期表

记录已完成主题、核心能力掌握率、最弱主题、重复错误、下一周期重点和是否调整计划。

完成度不能只有“已完成/未完成”，建议使用：

- `0`：未开始；
- `1`：看过但不能独立执行；
- `2`：能完成但不稳定；
- `3`：能限时独立完成并解释；
- `4`：随机变式也稳定。

## 9. 交付前校验

- 所有用户指定的 Markdown 是否已纳入？
- 是否有明确的 SMART 五维？
- 是否有优先级和阶段安排？
- 每项任务是否有输出物和验收条件？
- 是否包含当前重点和下一步动作？
- 是否有错题/问题复盘机制？
- 是否明确了假设、缺口和补充知识？
- 原始文件的修改时间和内容是否保持不变？
